# Демо-стенд «Комнаты команды» — 5 минут без агентов и трат

Демо — это **тот же интерфейс**, что и боевая комната, но с мок-движком: запросы
живут в памяти, карточки не уходят на доску, агенты Hermes не запускаются,
токены не тратятся. Всё, что видно на экране, выдумано для показа.

- Адрес по умолчанию: **http://127.0.0.1:8778**
- Боевой стенд (настоящая доска и агенты): http://127.0.0.1:8777 — см. `README.md`
  и `docs/USER-GUIDE.md`; в демо его трогать не нужно.
- Плашка в сайдбаре «ДЕМО — данные выдуманные, агенты не запускаются» и заголовок
  вкладки «ДЕМО · Комната команды» появляются только у мока (`engine.mock: true`).

## Запуск и остановка

Нужны Windows и Python 3.11+ в `PATH`. Порт 8778 должен быть свободен.

```bat
start-demo-room.cmd
```

Скрипт поднимает мок в фоне, пишет лог в `data\logs\demo.log`, PID — в
`data\run\demo-8778.pid`, и **не открывает браузер** (так задумано). Откройте
http://127.0.0.1:8778 вручную.

Полезные варианты:

```bat
start-demo-room.cmd --port 8785       :: другой порт
start-demo-room.cmd --open            :: открыть браузер после старта
start-demo-room.cmd --no-browser      :: явно без браузера (поведение по умолчанию)
start-demo-room.cmd --phase-scale 2   :: медленнее: один запрос идёт ~70 секунд
stop-team-room.cmd                    :: остановить 8777 и 8778
stop-team-room.cmd --port 8785        :: остановить только тестовый порт
```

`stop-team-room.cmd` убивает только процессы **python**, в командной строке
которых есть `team-room`; чужой процесс на порту он не тронет и скажет об этом.
PID-файл — первый способ найти процесс, порт — запасной.

## Что потрогать за 5 минут

| Минута | Шаг | Что должно быть на экране |
|---|---|---|
| 0:00 | Откройте http://127.0.0.1:8778 | Слева плашка «ДЕМО — данные выдуманные, агенты не запускаются», в заголовке вкладки «ДЕМО · Комната команды». Две комнаты: первая (с критиком) и вторая (без критика) — названия в демо выдуманы |
| 0:30 | Первая комната → вкладка **Запрос** | Пять карточек запросов: «в работе», «проверка», «готово», «нужен ответ». Это живые состояния демо-данных, а не картинка |
| 1:00 | Откройте «Каналы продаж: Едок или Развоз» | Готовый ответ с таблицей каналов, версией v2, проверкой критика; справа — вопрос владельцу и следующие шаги |
| 1:30 | Вернитесь в «Запрос» и отправьте свой текст (пример ниже) | Сразу появляется карточка «в очереди», через ~4 с — «в работе», руководитель комнаты раскладывает её на четыре ветки |
| 2:00 | Смотрите «Дерево работ» и «Хронологию» | Четыре карточки с осмысленными названиями (факты, цифры, риски, свод), исполнители из команды, статусы «ждёт → идёт → готово» |
| 2:20 | Дождитесь «проверка» (~12 с) | Появляется карточка критика «Критик: проверка свода (раунд 1)», ответ ещё не финальный |
| 2:40 | Дождитесь «готово» (~35 с) | Ответ v1, таблица, **интерактивный отчёт**: таблица веток, график уверенности, кольцевая диаграмма, граф «Кто что сделал»; справа вопрос владельцу |
| 3:20 | Ответьте на вопрос справа | Вопрос помечается «отвечено», счётчик «Ждёт тебя» уменьшается, запрос остаётся «готово» — ответ учтён |
| 3:40 | Нажмите **«На доработку…»** и напишите замечание | Появляется версия v2: переключатель v1/v2, в тексте блок «Что изменилось в версии 2», в дереве — карточка доработки |
| 4:20 | Вкладки **Карта проекта**, **Дальше**, **Отчёты**, **Журнал** | Этапы первой комнаты, решения, бэклог с датами, три отчёта, лента событий. Переключитесь на вторую — комната без критика, свой состав |
| 5:00 | `stop-team-room.cmd` | Сервер остановлен, порт свободен, `data\run\demo-8778.pid` удалён |

Пример запроса для проверки сценария:

```
Упаковка первого тиража: сравни трёх поставщиков коробов в Заозёрье —
цену, MOQ и срок. Для 100 наборов моти нужна рекомендация: у A MOQ 100,
у B 300, у C 500.
```

Мок выбирает один из пяти сценариев по словам в тексте: каналы продаж,
упаковка, бренд и знак, ИП/юридика и общий разбор. Тексты карточек, ответа,
отчёта и вопроса подставляются из сценария — это не настоящий анализ.

## Что происходит после «Отправить»

1. **Очередь (0–4 с).** Карточка «в очереди», дерево — только корень.
2. **Работа (4–12 с).** Руководитель комнаты раскладывает запрос на четыре ветки; агенты
   берут карточки, часть уже закрыта, часть ещё ждёт.
3. **Проверка критика (12–20 с).** Критик комнаты проверяет свод; в дереве
   появляется его карточка, в блоке «Проверка критика» — раунд 1.
4. **Свод (20–35 с).** Руководитель комнаты собирает финальный ответ; в этот момент уже
   виден черновик v1 и отчёт.
5. **Готово (35 с).** Версия v1, вопрос владельцу, кнопки «На доработку…»,
   «Копировать», «Скачать .md».
6. **Доработка.** «На доработку…» → 15 секунд → версия v2; история версий
   и карточка доработки сохраняются в памяти до перезапуска мока.

`--phase-scale` делит длительности: `0.5` — вдвое быстрее, `2` — вдвое медленнее.
Значение по умолчанию `1` — как в жизни, 35 секунд.

## Что нового: сообщение руководителю, папка проекта

**Диалог по запросу (волна 8).** На странице запроса под ответом есть блок «Диалог по
запросу»: лента сообщений владельца, ответы команды с ролью (например, «<профиль> ·
руководитель комнаты») и тонкие серые системные строки («Версия 2 готова»).
Внизу — поле ввода с микрофоном и кнопкой «Отправить руководителю»; у незавершённого
запроса есть галочка «Срочно: пересмотреть план целиком».

В демо сообщение принимается сразу (`POST /api/requests/{rid}/messages`), а через 3–6
секунд приходит правдоподобный ответ руководителя комнаты: «Принял: … Передал: <роль> —
каналы и продвижение…» и системное событие. Кому передать, мок решает по словам в
тексте (упаковка → операции, каналы → маркетинг, Роспатент/ИП → юрист, цифры → экономист).
Если отправить второе сообщение, пока ответ не пришёл, оно пакетируется в то же
уточнение. Для готового запроса сообщение запускает «На доработку»: версия N+1
появляется в ленте как «Версия N готова», запрос ненадолго уходит в доработку и
возвращается в «готово». Пустой текст → ошибка по-русски, ничего не отправляется.

**Папка проекта у комнаты.** В настройках комнаты есть поле «Папка проекта»; у первой — `<диск>:\Projects\<название комнаты>`, у второй — свой путь.
Проверка пути (`POST /api/rooms/check-dir`) отвечает, существует ли папка, будет ли она
создана и какие есть предупреждения: системные каталоги Windows и служебная папка
Hermes запрещены, `\\сервер\папка`, путь с «..» и зарезервированные имена (CON, COM1…)
не принимаются, папка внутри Vault разрешена, но с предупреждением.

Важно: **демо ничего не создаёт и не читает на диске** — `exists` и `will_create` мок
считает по своей таблице демо-каталогов, а сохранение комнаты только записывает путь в
память. В боевом стенде папка создаётся на самом деле.

**Бэклог собирается из всех запросов.** Вкладка «Дальше» показывает шаги, вопросы и
решения каждого запроса обеих комнат; отметка шага (`POST /api/rooms/{room}/backlog/{id}`)
больше не даёт «Элемент бэклога не найден»: если шага ещё нет в бэклоге, мок берёт его
из запроса и дописывает.

## Проектный режим в демо

Волна 9: у комнаты есть **карта проекта** — направления, которые руководитель
предлагает по брифу. В демо обе комнаты уже с картой (`fixtures/plan_cafe.json`,
`plan_fn.json`), поэтому вкладку «Карта проекта» видно сразу.

- **Первая комната — идёт работа:** 5 направлений. «Рецептура моти» — готово, «Упаковка и бренд» —
  в работе (под-запрос `t_9f3c2a10`), «Цена и юнит-экономика» — в очереди (ждёт рецептуру
  и упаковку), «Продажи и доставка» — предложено (ещё не запускали), «Налоги и ИП» —
  ждёт снятия лимита модели (под-запрос `t_7d21b8c4`). В журнале плана — кто что изменил
  и почему.
- **Вторая комната — только черновик:** 3 направления в статусе «предложено», ничего не запущено;
  «Смета первого этапа» ждёт «Документы» и «Вода, свет, подъезд».

Что потрогать (порт 8778, вкладка комнаты → «Карта проекта»):

1. **«Запустить»** у направления или «Запустить всё» (`POST /api/rooms/{r}/plan/approve`).
   Мок уважает `depends_on` и `max_parallel_streams` комнаты (у первой 2, у второй 1): запускается
   столько направлений, сколько слотов, остальные ждут в очереди. Каждое запущенное
   становится под-запросом в ленте комнаты, у него есть ссылка на карту (`plan_link`).
2. **Дальше всё идёт само, в демо-темпе:** ~9 секунд «в работе», потом «на проверке»,
   через ~4 секунды — «готово»; освободился слот — стартует следующее из очереди.
   Направление с лимитом модели (`waiting_quota`) возвращается в работу через ~12 секунд,
   как будто квота освободилась.
3. **Правка карты:** «Изменить» (название, цель, срок, участники), «Добавить направление»
   (`POST .../plan/streams`), «Отложить» (`DELETE`, направление остаётся в карте со
   статусом «отложено»). Всё пишется в журнал плана с причиной.
4. **«Собрать карту из запросов комнаты»** (`POST .../plan/rebuild`): создаётся запрос
   «Собрать карту из запросов комнаты», через 5–8 секунд «приходит» ответ руководителя с
   новым черновиком карты (уже идущие направления он не останавливает).
5. **Главный запрос с флажком «Это бриф проекта»** (`POST /api/rooms/{r}/requests` с
   `brief: true`): через 5–8 секунд — ответ руководителя и черновик карты; у брифа в
   ответе есть `brief: true` и `streams_summary` («направлений: N, идёт: M»).
6. **Сообщение руководителю может изменить карту.** Напишите в диалоге брифа что-то про
   сертификацию, поставщиков, найм, сайт или деньги на старт — руководитель ответит
   «Добавил в карту направление «…» — запущу по вашему «Запустить»», а в журнале появится
   запись «добавил» с причиной.

**Особые указания участникам.** В диалоге комнаты (создание и правка) у каждого участника
есть раскрытие «Особые указания для этой комнаты» — 1–3 фразы, которые действуют только
здесь (у первой они есть у двух участников, у второй — у юриста). В демо они уже в фикстурах комнат:
`GET /api/rooms/{id}` отдаёт `agent_notes`, сохранение — `PUT /api/rooms/{id}/agents/{profile}/notes`
(`{text}`). Профиль не из состава комнаты → 400 «Профиль «…» не участвует в комнате»,
больше 8 000 знаков → 400, пустой текст — очистка. Ключи и пароли в тексте не блокируются,
но мок возвращает предупреждение `secret_in_notes` («уберите из указаний»). Файлы профилей
(SOUL.md, config.yaml) демо не трогает — только реестр комнаты.

**Модели участников.** У каждого участника в демо есть выбор «Модель»: провайдер, поиск модели,
«Размышление» и «Усилия», подпись «по умолчанию: …» и кнопка «Вернуть по умолчанию».
Каталог вымышленный — `GET /api/models`: три настроенных провайдера («Облако-А»,
«Локальный сервер», «Облако-Б») и один ненастроенный («Закрытый контур», `configured: false` —
его не должно быть в списке выбора), усилия от «без размышления» до «предельный».
Замена живёт только в комнате: у первого участника первой комнаты (`biz-ops`) и у юриста второй
(`lawyer`) модель уже изменена для комнаты (`source: "room"`), у остальных — как у агента.

Что потрогать: смена модели — `PUT /api/rooms/{id}/agents/{profile}/model`
`{provider, model, reasoning}`, ответ `{member, agent_models, applied: {cards_updated,
pending_running, cards_failed}, warnings}`; у карточек не в работе подпись меняется сразу,
у идущих — только после «Перезапустить на новой модели» (`POST …/restart` → `{restarted, cards}`),
поэтому в ответе `pending_running > 0` и предупреждение. Пустой объект (или `null` в теле) —
«вернуть по умолчанию». Ошибки по-русски, 400: профиль вне состава, ненастроенный провайдер,
модели нет в каталоге, недопустимые усилия. Каждое изменение пишется в журнал комнаты
(«Модель участника «…» изменена: провайдер · модель · мышление»), а на странице запроса у карточек
появляется мелкая подпись `model_label`. Файлы профилей демо не трогает — только реестр комнаты.

Лимиты демо совпадают с боевыми (`GET /api/config → limits`): тело запроса 8 МиБ, текст
запроса/сообщения до 1 000 000 знаков, комментарий/заметка — до 200 000, указания
участнику — до 8 000.

## Чем демо отличается от боевого стенда

| | Демо, порт 8778 (`start-demo-room.cmd`) | Боевой, порт 8777 (`start-team-room.cmd`) |
|---|---|---|
| Движок | мок в памяти, `engine.mock: true` | настоящий сервер + канбан-доска `team` |
| Агенты | не запускаются | реальные профили Hermes, реальные запуски |
| Токены и деньги | 0 | тратятся по тарифу провайдера |
| Доска и Vault | не читаются и не пишутся | карточки на доске, зеркало `STATE.md` в Vault |
| Данные | выдуманы, после перезапуска сбрасываются | реальные запросы, ответы и журнал |
| Плашка «ДЕМО» | есть | нет |
| Для чего | показать интерфейс, потрогать сценарий, снять скриншоты | работать над настоящими задачами |

Демо ничего не пишет в `%LOCALAPPDATA%\hermes`, `C:\TeamRoom\Vault` и на доску.
Единственные файлы — `data\logs\demo.log` (stdout и stderr), `data\run\demo-<порт>.pid`
и демо-словарь распознавания речи `data\dictation-demo\dictation\dictionary.json`.
Боевой словарь `data\dictation\` мок не трогает.

## Устройство демо

- `tools/mock_server.py` — HTTP-сервер: статика `web/`, `/api/*`, проверки
  Host/Origin, только loopback.
- `tools/mock_app.py` — состояние в памяти и эволюция живого запроса по фазам.
- `tools/mock_demo.py` — сценарии: дерево работ, тексты ответов, вопрос владельцу, следующий шаги и генерация интерактивного отчёта (таблица, два
  графика, граф).
- `tools/mock_read.py`, `mock_write.py`, `mock_core.py`, `mock_versions.py` —
  чтение фикстур, действия, общие помощники и расписание фаз.
- `tools/mock_plan.py` — карта проекта: очередь направлений (`depends_on`,
  `max_parallel_streams`), таймеры демо-темпа, правка/добавление/отложение,
  «Собрать карту», бриф и `streams_summary`/`plan_link` в запросах.
- `tools/mock_notes.py` — «Особые указания для этой комнаты»: проверка состава,
  лимит 8 000 знаков, предупреждение о секретах, `GET` комнаты с `agent_notes`.
- `tools/mock_models.py` — «Модель участника»: вымышленный каталог (`fixtures/models.json`),
  `GET /api/models`, `PUT …/agents/{profile}/model`, `POST …/restart`,
  `model_settings`/`agent_default` у участников, подпись `model_label` у карточек.
- `tools/mock_stt.py` — мост диктовки к `server/stt.py` (ленивый импорт): статус,
  расшифровка, словарь и обучение. Если распознавание на стенде не подключено,
  маршруты честно отвечают 503 «Распознавание речи на этом стенде ещё не подключено»,
  а не выдуманным текстом. Демо-словарь живёт в `data\dictation-demo\`.
- `fixtures/*.json` — демо-комнаты, запросы во всех состояниях,
  отчёты, бэклог, журнал.

Отчёт для нового запроса собирается из его же дерева: строки таблицы — карточки
веток, график — оценка уверенности, граф — связи «руководитель → ветки → критик →
доработка». Поэтому он выглядит согласованно с текстом запроса.

## Ограничения

- Все цифры, поставщики и сроки **выдуманы**. Решения по демо принимать нельзя.
- Данные живут в памяти: перезапуск мока возвращает исходные пять запросов.
- Демо не умеет запускать агентов и не проверяет реальные файлы: артефактов
  и `report.json` на диске нет, отчёт генерируется на лету.
- Сценарий выбирается по ключевым словам; для совсем постороннего текста
  сработает общий разбор «факты → цифры → риски → свод».
- Сервер слушает только `127.0.0.1`; с другого компьютера демо недоступно.

## Если что-то не так

| Симптом | Что делать |
|---|---|
| «Порт 8778 занят» | `stop-team-room.cmd`, затем запустите снова; или `start-demo-room.cmd --port 8785` |
| Браузер не открылся | Так и задумано: откройте http://127.0.0.1:8778 вручную или добавьте `--open` |
| Плашки «ДЕМО» нет | Вы на 8777 (боевой) или мок не ответил — проверьте `http://127.0.0.1:8778/api/health`, поле `engine.mock` |
| Демо не поднялось | `type data\logs\demo.log` — там traceback; проверьте Python в `PATH` |
